# Część 2: Indywidualny mini-projekt (100 pkt)

## Zasady

- Każdy student realizuje **jeden mini-projekt indywidualnie**.
- Mini-projekt powinien być **powiązany z tematyką kursu** (prawo, etyka, regulacje AI) i **najlepiej z projektem grupowym**.
- Wybiera się **jedno zadanie z menu** prowadzącego lub **proponuje się własne** (do zatwierdzenia na zajęciach).

### Zachęta do narzędzi AI

Do realizacji mini-projektów prowadzący **zachęca** do korzystania z narzędzi typu copilot / asystenci AI, m.in.:

| Narzędzie | Opis |
|-----------|------|
| **Claude Code** | Agent AI w terminalu (Anthropic) |
| **Codex** | Agent CLI (OpenAI) |
| **GitHub Copilot** | Asystent AI w VS Code, JetBrains, Neovim |
| **Cursor** | IDE z wbudowanym AI (fork VS Code) |
| **Windsurf** | IDE z AI, agentic editing |
| **Aider** | Open-source pair programming w terminalu |
| **OpenCode** | Open-source agent terminalowy |
| **Replit** | IDE w przeglądarce z AI Agent |
| **Bolt.new** | Budowanie full-stack aplikacji w przeglądarce |
| **Continue** | Open-source wtyczka AI do VS Code / JetBrains |

## Terminy i forma oddania

1. **Do 3. zajęć projektowych** każdy student musi mieć **ustalony i potwierdzony temat** mini-projektu z prowadzącym. **Bez potwierdzenia** — mini-projekt **nie będzie oceniony**.
2. **Oddanie mini-projektu** = **zaproszenie prowadzącego** do repozytorium **GitHub** (username: **`laugustyniak`**) zawierającego **kod, opis i efekty pracy**. Samo wysłanie linku **bez dostępu** **nie jest** traktowane jako oddanie.
3. Po upływie **ostatecznego terminu** prowadzący **automatycznie wykonuje kopię** repozytorium do oceny. Oceniany jest **stan repozytorium na moment terminu** — **późniejsze zmiany nie będą uwzględniane**.

---

## Co jest oceniane

Nie ocenia się, czy aplikacja jest „ładna”, ani czy wszystko działa perfekcyjnie. Ocenia się m.in.:

### Proces i dokumentacja (40 pkt)

Jak pracowaliście:

- Jakie **prompty / narzędzia GenAI** wykorzystaliście i do czego? **Pokazać rzeczywiste prompty.**
- Jakie **decyzje** podjęliście po drodze i **dlaczego**?
- **Co nie zadziałało** i **co z tym zrobiliście**?
- **README** z opisem: cel, jak uruchomić, co robi, **czego nie robi**.

### Merytoryka i głębokość analizy (40 pkt)

Czy mini-projekt pokazuje **zrozumienie aspektów prawnych / etycznych**:

- Czy wyciągnęliście **wnioski z wyników**?
- Czy analiza jest **pogłębiona**, a nie powierzchowna?
- Czy **powiązaliście wyniki z projektem grupowym**?

### Techniczna realizacja (20 pkt)

Kod / notebook:

- Czy kod jest **czytelny i zrozumiały**?
- Czy można go **uruchomić** / **zreprodukować wyniki**?
- **Nie musi być produkcyjny** — notebook lub skrypt z komentarzami wystarczy.

---

## Skalowanie ocen — co na jaką ocenę

| Poziom | Opis |
|--------|------|
| **Base (50–60%)** | Podstawowa implementacja: działa, jest udokumentowana, ma wnioski. Np. skrypt skanujący licencje w jednym repo + tabelka wyników. |
| **Good (70–80%)** | Głębsza analiza: porównanie podejść, więcej danych, lepsze wnioski. Np. skan licencji + analiza kompatybilności + rekomendacje. |
| **Excellent (90–100%)** | Kompleksowe podejście: twórcze rozwiązanie, pogłębiona analiza, silne powiązanie z projektem. Np. pipeline audytu licencji z CI/CD + raport kompatybilności + policy dla zespołu. |
